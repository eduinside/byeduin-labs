# 협의 도우미 (옛 이름 협의 날짜 모으기, 주소 `apps/meeting-helper`, 옛 주소 `apps/meet-date` → 301, API `/api/meet-date` 그대로) 계획

> 상태: **2단계 구현 (2026-11-27)** - §11 세 가지 종류·서명·안내 기능까지. 처음 1단계 결정 중 '서명 그림 서버 저장 안 함'은 §11-2에서 바뀜(운영자 승인). 아래는 1단계 당시 메모: — §10 결정: 이름 '협의 날짜 모으기', 마감 30일 뒤 삭제, 기본 양식은 자체 명단형, 서명 그림 서버 저장 없음. 2단계 남음.

## 1. 왜 만드나

학교 업무에서 협의는 보통 `협의 → 협의록 작성 → 등록부(참석 일시 + 서명) 작성` 순서로 진행한다.
문제는 날짜 맞추기다. 담당자가 메신저로 "언제 되세요?"를 돌리고, 답을 표로 옮기고, 다시 등록부 양식을
한 명씩 받아 모으는 데 시간이 많이 든다.

이 도구로 바꾸는 것:

| 지금 | 바꾼 뒤 |
|---|---|
| 메신저로 가능한 날짜를 묻고 손으로 정리 | 링크 하나 보내면 응답이 표로 모임 |
| 등록부 양식을 따로 보내고 따로 받음 | 응답자가 시간을 고르면 그 자리에서 내 등록부(HWPX)가 만들어짐 |
| 서명이 필요 없는 경우에도 파일을 주고받음 | 이름만 적어 제출 → 담당자가 전체 명단 등록부를 한 번에 받음 |

원칙: **로그인 없음, 입력 최소(이름 1칸), 서명 그림은 서버에 저장하지 않음, 마감 뒤 자동 삭제.**

## 2. 사용자와 흐름

### 2-1. 담당자 (만드는 사람)

1. **협의 만들기** 화면에서 적는다.
   - 협의 제목, 협의 내용(짧은 글), 장소(선택)
   - 방식 고르기
     - **A. 후보 중에서 고르기** — 기간(예: 12/1~12/12) + 요일 + 시간대(예: 15:00~16:00, 16:00~17:00)를 정하면 후보 칸이 자동으로 만들어짐. 칸을 눌러 빼거나 더할 수 있음.
     - **B. 직접 적기** — 기간만 정하고, 응답자가 그 안에서 날짜·시작·끝 시간을 직접 입력(연수·개별 협의처럼 각자 날짜가 다른 경우).
   - **몇 개 고르게 할지** — 정확히 N개 / 최소 N개 / 제한 없음
   - **한 시간대 정원**(선택) — 칸마다 최대 인원(개별 면담·소그룹 협의). 꽉 찬 칸은 응답자 화면에서 막힘.
   - **받을 정보** — 이름(필수), 소속·학년반·과목 등 담당자가 고른 칸(선택), 의견 한 줄(선택)
   - **등록부 양식** — §5
   - 마감 일시, 응답자에게 다른 사람 응답 보여 주기 여부(기본 끔)
2. 저장하면 **링크 두 개**가 나온다.
   - **응답 링크** `eduin.info/apps/meet-date/#m=AB3K9Q` — 메신저로 보냄(단축 주소 `/api/shorten`, QR 같이 제공)
   - **관리 링크** `…/#m=AB3K9Q&k=<관리키>` — 담당자 본인만. 브라우저에도 기억(localStorage)하고 "관리 링크를 잃으면 다시 열 수 없습니다" 안내
3. **관리 화면**
   - 응답 현황(몇 명 응답 / 이름 목록)
   - 시간대별 가능 인원 표(가장 많이 되는 칸 강조) — 방식 A
   - 응답자별 날짜 목록 — 방식 B
   - **확정하기**: 칸 하나(또는 여러 개)를 확정 → 응답 링크로 다시 들어온 사람에게 "확정: 12/5(목) 15:00" 표시
   - **전체 등록부 받기**(HWPX, 명단형) · **엑셀(CSV) 받기**
   - 응답 하나 지우기, 협의 전체 지우기, 마감 연장

### 2-2. 응답자 (받는 사람)

1. 링크를 열면 협의 제목·내용·기간이 보임.
2. 되는 시간을 고름(방식 A: 칸 누르기 / 방식 B: 날짜·시간 입력, 여러 줄).
3. 이름(과 담당자가 요청한 칸) 입력. 한 번 쓴 이름·소속은 이 브라우저에 기억해 다음 협의에서 자동 입력.
4. 제출 방법 고르기 (담당자가 허용한 것만 보임)
   - **이름만 적어 제출** — 서버에 응답 저장, 끝. 담당자 등록부의 서명란에 이름이 들어감(또는 빈칸, 담당자 설정).
   - **서명해서 파일로 보내기** — 화면에 손글씨 서명(캔버스) → 내 등록부 HWPX가 브라우저에서 만들어져 내려받음 → 메신저로 담당자에게 따로 보냄. 이때도 일정 응답 자체는 서버에 저장되어 담당자 표에 모임.
   - **한글에서 직접 서명** — 서명 없이 내 등록부 HWPX만 받아 한글에서 서명 그림 넣고 보냄.
5. 제출 뒤 "내 응답 고치기/지우기" 가능(브라우저에 응답 키 저장). 확정되면 같은 링크에서 확정 일시 확인.

## 3. 저장 방식 결정: URL만 쓸까, D1을 쓸까

| | URL만(서버 저장 없음, vives-share 해시) | **D1 저장 (추천)** |
|---|---|---|
| 협의 정보 전달 | `#share=` 에 통째로 인코딩 | 6자리 코드만 링크에 |
| 응답 모으기 | 응답자가 '응답 링크'를 담당자에게 다시 보내고, 담당자가 붙여 넣어 합침 | 자동으로 모임 |
| 정원·중복 막기 | 불가 | 가능 |
| 확정 알림 | 담당자가 다시 링크를 돌려야 함 | 같은 링크에서 보임 |
| 개인정보 | 서버에 없음 | 이름·소속이 D1에 잠시 저장(마감 후 자동 삭제) |
| 링크 길이 | 후보가 많으면 김 | 짧음 |

날짜 조율의 핵심 불편이 '모으기'라서 **D1 저장을 기본**으로 한다. 저장하는 개인정보는 이름과 담당자가 고른
칸뿐이고, 서명 그림은 저장하지 않는다. vives-share 패턴은 다음 두 곳에 쓴다.

- **양식 복제 링크**: 담당자가 만든 협의 설정(내용·후보 규칙·등록부 양식)을 `#share=`로 동료에게 넘겨 "이 설정으로 새 협의 만들기"(clone 권한). 응답 데이터는 넣지 않음.
- **서버 장애 대비**: D1 저장이 실패하면 응답 내용을 `#r=` 인코딩 링크로 만들어 "이 링크를 담당자에게 보내 주세요"로 안내(관리 화면에 붙여 넣기 칸).

## 4. 데이터 설계 (D1 `BYEDUIN_DB`, 접두사 `meet_`)

```sql
CREATE TABLE meet_events (
  id          TEXT PRIMARY KEY,      -- 6자리(혼동 문자 제외, 마당 BOARD_RE와 같은 규칙)
  owner_hash  TEXT NOT NULL,         -- HMAC(pepper, 'owner:'+id+':'+관리키). 관리키 원본 미저장
  config      TEXT NOT NULL,         -- JSON: 제목·내용·방식·후보 칸·선택 수·정원·받을 칸·양식 설정 (≤32KB)
  confirmed   TEXT,                  -- JSON: 확정된 칸 id 목록
  closes_at   TEXT NOT NULL,         -- 응답 마감
  purge_at    TEXT NOT NULL,         -- 자동 삭제 시각(마감 + N일, §10)
  created_at  TEXT NOT NULL,
  rev         INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE meet_responses (
  event_id    TEXT NOT NULL,
  id          TEXT NOT NULL,         -- 응답 id(무작위)
  edit_hash   TEXT NOT NULL,         -- HMAC(pepper, 'resp:'+event+':'+id+':'+응답키)
  name        TEXT NOT NULL,         -- ≤20자
  fields      TEXT,                  -- JSON: 소속 등 담당자가 고른 칸 (≤1KB)
  picks       TEXT NOT NULL,         -- JSON: 방식 A 칸 id 목록 / 방식 B [{date,start,end}]
  sign_mode   TEXT NOT NULL,         -- 'name' | 'file' | 'hwp'
  updated_at  TEXT NOT NULL,
  PRIMARY KEY (event_id, id)
);
```

- API 하나: `functions/api/meet-date.js`
  - `GET ?m=` 협의 보기(응답자용 config + 칸별 인원 수, '다른 응답 보기' 켰을 때만 이름)
  - `GET ?m=&k=` 관리용 전체(응답 목록 포함)
  - `POST` 만들기 / `PUT` 수정·확정·연장 / `DELETE` 삭제 (관리키 필요)
  - `POST ?m=/resp` 응답 제출, `PUT`·`DELETE` 응답 고치기·지우기(응답키 필요)
- 정원 검사는 서버에서(동시 제출 대비 `INSERT … SELECT … WHERE count < cap` 한 문장 또는 batch).
- 남용 방지: `_guard.js`에 `meet-create`(IP당 하루 30개), `meet-resp`(분당 60, 하루 600) 추가, `checkOrigin`, 본문 상한. 협의당 응답 300개 상한.
- **자동 삭제**: Pages Functions에는 cron이 없으므로, API 호출 때 `DELETE … WHERE purge_at < now` 를 가끔(확률 1/50) 실행 + 지난 협의는 읽기 시 404. (별도 Worker cron이 필요해지면 그때 운영자 확인)
- 무료 티어 영향: 협의 1건 = 쓰기 수십 회 수준, D1 무료 한도(일 10만 쓰기) 대비 무시할 만함.

## 5. 등록부(HWPX) 만들기

### 5-1. 기본 원칙

- **브라우저에서 만든다.** 서버로 서명·이름을 보내지 않는다. JSZip(파일 도구에서 이미 사용)으로
  견본 HWPX를 열어 `Contents/section0.xml`의 자리표시를 바꾸고 다시 묶는다(`mimetype` 무압축 유지).
- 견본 파일은 `public/apps/meet-date/forms/*.hwpx`로 둔다. 한글에서 직접 만든 양식에
  `{{제목}}` 같은 자리표시를 넣어 저장한 것.

### 5-2. 기본 양식 두 가지

| 양식 | 누가 받나 | 내용 |
|---|---|---|
| **개인 등록부** | 응답자(서명해서 보내기·한글에서 서명) | 협의명, 일시(고른 칸 또는 확정 일시), 장소, 소속, 이름, 서명(그림 또는 빈칸) |
| **명단형 등록부** | 담당자(관리 화면) | 협의명·일시·장소 머리말 + 표: 번호·소속·이름·참석 일시·서명란(이름/빈칸) |

### 5-3. 담당자가 바꿀 수 있는 것 (쉬운 것부터)

1. **글자 바꾸기**: 문서 제목('협의회 참석 등록부' → '연수 등록부'), 머리말 문장, 맨 아래 확인 문구.
2. **칸 켜고 끄기**: 소속·학년반·과목·연락처·의견·서명 칸. 꺼진 칸은 표에서 열/줄 삭제.
3. **서명란 채우는 방식**: 이름 넣기 / 빈칸 / '(서명 파일 별도)'.
4. **내 양식 올리기**(2단계): 담당자가 한글에서 만든 HWPX에 자리표시를 넣어 올림 → 브라우저에서 자리표시
   목록을 읽어 보여 주고, 빠진 필수 자리표시를 알려 줌. 올린 양식은 서버에 올리지 않고 담당자 브라우저에만
   저장(IndexedDB). 응답자에게 '개인 등록부'를 내 양식으로 주려면 양식을 R2에 올려야 하므로 3단계에서 따로 검토.

자리표시 목록(초안): `{{제목}} {{내용}} {{장소}} {{일시}} {{이름}} {{소속}} {{의견}} {{서명}} {{작성일}}`,
명단 표는 견본 표의 둘째 줄을 `{{#명단}}…{{/명단}}` 반복 줄로 보고 응답 수만큼 복제.

### 5-4. 서명 그림 넣기

- 캔버스 서명 → PNG(투명 배경, 가로 400px) → HWPX `BinData/`에 추가, `Contents/content.hpf` manifest 등록,
  `{{서명}}` 자리에 `hp:pic` 삽입(크기 약 30×12mm). 파일 도구의 HWPX 그림 처리 코드(`collectHwpxUses` 근처)를 참고.
- 서명 그림은 이 과정에서만 메모리에 있고 저장·전송하지 않는다.
- 검증: kordoc `render_document`로 견본별 결과를 그려 보고, 한글 2020/2024에서 열어 확인.

## 6. 화면 구성

`src/pages/apps/meet-date/index.astro`(AppLayout) + `public/apps/meet-date/app.js`. 해시로 화면 전환.

| 해시 | 화면 |
|---|---|
| (없음) | 시작: '새 협의 만들기' + 내가 만든 협의 목록(브라우저 기억) |
| `#new` | 만들기(단계 3개: 내용 → 날짜·시간 → 받을 정보·등록부) |
| `#m=CODE` | 응답 |
| `#m=CODE&k=KEY` | 관리 |
| `#share=…` | 설정 복제(vives-share) |

- 방식 A 후보 칸은 '날짜 × 시간대' 격자. 휴대폰에서는 날짜별 목록으로 바뀜(메신저로 받아 폰에서 여는 경우가 많음).
- 공용 UI: `VUI.share.link`(단축+복사+QR), `VSafe`(입력 검증), 토스트·모달은 `common/ui.js`.
- 화면 글은 CLAUDE.md '화면 글투' 기준(예: '판정' 대신 '결정', '칸'은 실제 표의 칸일 때만).

## 7. 개인정보

- 수집: 이름(필수), 담당자가 고른 칸(선택). 수집 목적·보관 기간을 응답 화면 제출 버튼 위에 한 줄로 표시
  ('이 협의 일정 조율과 등록부 작성에만 쓰며 OO일에 자동 삭제됩니다').
- 연락처 칸은 기본 목록에서 빼고, 담당자가 굳이 켤 때 경고 문구.
- 서명 그림: 서버 저장·전송 없음.
- 관리키·응답키는 원본 저장 없이 HMAC만(마당 방식). 관리 링크는 `#` 뒤에 있어 서버 로그에 남지 않음.
- 담당자 '전체 지우기' 즉시 삭제, 응답자 '내 응답 지우기' 즉시 삭제.

## 8. 단계별 일정

| 단계 | 범위 | 분량 |
|---|---|---|
| **1단계 (MVP)** | 방식 A·B, D1 저장, 관리 화면(현황·인원 표·확정), 이름만 제출, 명단형 등록부 HWPX(기본 양식, 글자 바꾸기·칸 켜고 끄기), CSV | 3~4일 |
| **2단계** | 개인 등록부 + 캔버스 서명 HWPX, 한글에서 서명용 빈 등록부, 정원, 설정 복제 링크(vives-share), 장애 대비 `#r=` 링크 | 2~3일 |
| **3단계** | 내 양식 올리기(자리표시 검사), 확정 후 협의록 HWPX 초안(협의명·일시·참석자·협의 내용 채움, 결과는 담당자가 작성), 캘린더(.ics) 받기 | 필요 시 |

## 8-1. 1단계 구현 메모

- 정원(한 시간대 최대 인원)은 2단계로 미룸. 확정은 후보 방식은 칸 id 목록, 직접 적기는 담당자가 확정 일시를 적는 방식.

### 11-2. 실시간 등록부

- 담당자: 관리 화면 '출석 받기' → 전체 화면 QR + 들어온 사람 목록(5초마다 새로 고침, rev 비교로 바뀐 때만 받음). 열고 닫기 버튼(닫으면 더 못 냄).
- 참석자: QR → 이름(+소속) → 서명 칸에 손가락으로 서명(캔버스, 지우고 다시) → 제출. 일정 정하기에서 같은 브라우저로 응답했던 사람은 이름이 미리 채워짐.
- 서명 저장: PNG(흰 바탕 없이 투명, 가로 400px, 보통 5~15KB)를 D1 `meet_signs`에 base64로(장당 30KB 상한, 협의당 300장). 마감 30일 뒤 함께 삭제, 담당자가 등록부를 받은 뒤 '서명 지우기'로 바로 지울 수 있음. **1단계 결정(서명 서버 저장 안 함)을 바꾸는 부분 - 운영자 확인 필요.**
- 등록부: 서명란에 그림 넣기(`BinData/` + `content.hpf` 등록 + `hp:pic`, 약 30×12mm). hwpx.js에 그림 넣기 추가.

### 11-3. 활동 날짜 받기 + 확인서

- 응답 제출 뒤 '내 활동확인서'(개인 양식: 활동명·활동 일시 N개·이름·소속·서명·확인 문구·담당자) HWPX를 브라우저에서 만든다. 서명은 화면 손글씨(파일에만 들어가고 서버로 안 감) 또는 비워 두고 한글에서.
- 내는 방법(담당자가 허용한 것만):
  - **파일로 보내기(수동)**: 받아서 메신저로 보냄. 담당자 응답 표에 '받음' 체크.
  - **바로 내기**: 서명을 서버에 같이 저장(11-2와 같은 `meet_signs`) → 담당자가 확인서를 한 번에 받기(사람마다 한 쪽씩 이어 붙인 HWPX 하나, 또는 명단형).
- 담당자 표에 제출 상태 칸: 응답만 / 파일 받음 / 바로 냄.

### 11-6. 2단계 구현 메모 (2026-11-27)

- `config.kind`: schedule·activity·live. live는 `session {d,s,e}` 하나(range = 그날), 출석 열림은 `meet_events.live_open`. 일정 정하기에서도 관리 화면 '실시간 출석'으로 같은 출석 화면을 쓴다(활동 종류는 숨김).
- 출석 링크 `#s=CODE`(live 종류는 `#m=`로 와도 `#s=`로 바꿈). 서명키는 브라우저(`vives-meet:s:CODE`)에 두고 '다시 서명하기'로 고침.
- 담당자 화면은 출석 받는 중일 때 5초(큰 화면 3초)마다 `GET ?signs=1&after=` — 바뀐 서명만 그림과 함께 받음. 멈추면 부르지 않음.
- 확인서 바로 내기 = `meet_signs` id `c`+응답id(kind cert) + `meet_responses.status='direct'`. 응답에서 날짜나 이름을 바꾸면 바로 낸 표시와 서명을 풀고 다시 내게 함. 파일로 받은 것은 담당자가 '파일 받음' 체크(`status='file'`).
- 서명 PNG 검사: `data:image/png;base64,` + PNG 머리 바이트 + 40,000자 상한. 화면에는 같은 형식 검사 뒤에만 `<img src>`로.
- 안내 문구는 종류·확정 여부에 따라 틀로 만든다(일정 확정 안내·응답 요청·출석 안내·독촉). 받을 사람 명단은 담당자 브라우저(`vives-meet:expect:CODE`)에만.
- 설정 복제: 제목·내용·장소·방식·횟수·받을 정보·양식·내는 방법·시간대·요일(날짜는 새로). 응답·서명은 넣지 않음.
- 남은 것: 정원(한 시간대 최대 인원), 내 양식(HWPX 자리표시) 올리기, 확정 후 협의록 초안.

## 12. 담당자 사이드바·구글 캘린더 링크 (2026-11-27, 운영자 요청)

- **사이드바는 담당자 화면에만**: 만들기(`#new`·`#edit`)와 관리(`#manage`). 받은 사람 화면(응답 `#m=`·서명 `#s=`)은 지금처럼 가운데 한 줄로 단순하게 두고, 위에 '협의 도우미 처음 화면' 버튼만 둔다. 처음 화면(종류 고르기·내 목록)은 그 자체가 메뉴라 사이드바 없이 둔다.
- **사이드바 내용**: ① 처음 화면 ② 새로 만들기(일정 정하기·활동 확인서·실시간 등록부) ③ 이 협의 단계 — 만들기는 종류·내용·날짜와 시간·받을 정보·양식·마감, 관리는 링크 보내기 → 시간별로 보기(응답 수·확정 표시) → 실시간 출석(서명 수) → 응답한 사람 → 받기 → 안내하기 → 관리. 보이는 칸만, 누르면 그 칸으로 이동, 스크롤 위치에 따라 지금 단계 표시 ④ 내 협의(이 브라우저의 `vives-meet:mine`, 지금 협의 표시)로 다른 협의로 바로 이동.
- **화면 폭**: 사이드바가 있는 화면은 `data-width="wide"`(JS로 바꿈), 900px 아래에서는 사이드바가 맨 위 접힌 '메뉴' 상자가 된다(서랍·햄버거 없이 `<details>`).
- **구글 캘린더**: `.ics` 받기를 없애고 구글 캘린더 '일정 추가' GET 주소(`calendar.google.com/calendar/render?action=TEMPLATE&text&dates&ctz=Asia/Seoul&details&location`)를 쓴다. 받은 사람 화면은 확정 일정마다 '구글 캘린더에 넣기' 링크, 관리 화면 안내하기는 '구글 캘린더 링크'로 일정별 주소를 글로 보여 주고 복사. 시각은 한국 시간 그대로 두고 `ctz`로 시간대를 알려 준다(보는 사람 기기 시간대와 무관).

## 13. VIVES 싱크로 '내 협의' 묶기·참여 목록·첫 화면 사이드바 (구현 2026-11-27, 운영자 승인)

**하고 싶은 것**: 담당자가 관리 링크를 따로 챙기지 않아도, VIVES 동기화 코드(`vives:code`, 6자리, 사이트 공용)가 있는 기기면 어디서든 자기가 만든 협의를 연다. 응답하는 사람은 코드 없이도 그대로 응답하고, 코드가 있으면 참여 기록이 기기 사이로 따라간다. 첫 화면부터 사이드바.

**방식**: 협의 권한 구조(협의마다 22자 관리키)는 그대로 두고, 그 열쇠 목록을 동기화 문서에 담는다.
- 새 동기화 문서 `/api/meeting-helper-sync`(VivesSync doc 모드, 표 `meet_sync_docs`, 마이그레이션 0018). 내용 `{ mine:[{id,key,title,kind,at}], joined:[{id,kind,title,rid,rkey | sid,skey,at}] }`.
- 기기끼리 덮어쓰지 않게 받아 온 뒤 협의 id 기준으로 합치고(최근 것 우선, 지운 것은 `removed` 표시) 올린다.
- **만들 때는 코드 필수**: 코드가 없으면 '코드 만들기 / 가진 코드 넣기'를 먼저 띄운다. 관리 링크는 '다른 방법으로 열기'로 접어 둔다(코드를 잃었을 때 대비).
- **응답·서명은 코드 없이**: 지금처럼 이 브라우저에 응답키를 두고, 코드가 있으면 참여 목록이 동기화 문서에도 올라간다.
- **첫 화면**: 사이드바(처음 화면·새로 만들기·내가 만든 협의·내가 참여한 협의·동기화 코드) + 본문에 '내가 참여한 협의' 카드(확정 일시·내가 고른 시간·제출/서명 여부·마감)와 '내가 만든 협의' 카드(응답 수·확정 여부). 상태는 화면을 열 때 협의마다 불러온다(많으면 최근 12개).

**짚어 둘 점(보안)**: 동기화 코드 6자리가 곧 '내가 만든 협의 모두의 열쇠 꾸러미'를 여는 열쇠가 된다. 지금 사이트 공용 동기화 GET에는 읽기 제한이 없으므로, 이 문서의 GET에는 `meet-read` 제한(분당·하루)을 건다. 참석자 이름·서명이 들어 있는 협의라서, 코드를 남에게 보여 주지 말라는 안내를 만들 때 함께 띄운다.

**바뀌지 않는 것**: 받은 사람 화면(응답·서명)은 사이드바 없이 단순하게. 협의 API·D1 협의 표는 그대로.
